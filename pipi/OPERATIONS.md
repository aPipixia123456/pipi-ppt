# 部署、验收与运维

## 主站服务器的域名接入

主站目前使用 Docker 中的 Caddy，不能直接安装仓库的 Nginx 示例覆盖现有入口。在现有 Caddyfile 中导入独立的 PPT 配置；验收前使用 `ops/Caddyfile.ppt-maintenance.example`，验收通过后换成 `ops/Caddyfile.ppt.example`。先执行 `caddy validate`，再热加载，分别复核 PPT 的 HTTPS、HTTP 跳转及主站 `/api/status`。不要重启主站容器来申请证书。

2026-10-09 检查时，`ppt.pipixia1.online` 与主站均解析到 `154.9.232.22`；主站为 8 GB 内存，约 1.8 GB 可用。不能直接按默认生成/导出并发启动完整 PPT 部署栈。公开生成前需安排独立服务器或增加资源，并完成实际负载验证；DNS 与 HTTPS 接通不代表授权、生成和计费已上线。

## 首次公开启用前

- 将 pipiapi 的授权回调与本站 `PIPI_PUBLIC_URL` 精确对齐，验证 HTTPS、Host 与 Origin。
- 测试两名真实账户并发执行文字、视觉和图片调用；在 pipiapi 余额/套餐/日志中对比费用归属。模型必须支持 JSON 对象、图片输入和指定图片尺寸/base64 输出。
- 测试拒绝授权、重复兑换、过期、跨用户访问、撤销、安全版本失效、余额不足、套餐限制、429、部分成功、超时和取消。
- 在 PostgreSQL 中重启 Worker 与 Redis，确认已消费步骤不会重发。待确认任务不能一键自动重试；先查看 pipiapi request_id 与账单。
- 在 PowerPoint 和 WPS 打开内置和上传模板导出的 PPTX，检查中文长文、缺失字体、Logo、表格和图表的可编辑性与位置，PDF 与 PPTX 对照。
- 在 pipiapi 的 SQLite/MySQL/PostgreSQL 环境运行应用授权迁移/测试。网站自身使用独立 PostgreSQL。
- 最后由管理员启用新任务。所有有效 pipiapi 用户均可通过同一授权入口访问，无邀请白名单。

## 运行限制

默认每人一个执行中/三个排队任务，全站四个生成/两个导出。数据库锁和条件更新控制调度；Redis 消息重复不会绕过数据库状态。用户端幂等键和网关步骤幂等分别防止重复建任务和重复模型请求。

上传 20 MB/30 页、每用户 1 GiB；管理员可下调文件限制及调整存储和并发。转换子进程限时 90 秒，Worker 硬限时 510 秒；10 分钟无进展的任务由调度器检查恢复。只允许无宏 PPTX，转换容器以非 root 用户、只读根目录、移除 capabilities、CPU/内存/PID 限制运行。生产还应在防火墙限制 Worker 出站到 pipiapi，禁止转换子进程访问内网服务；不能仅依靠文档解析器防御不可信文件。

临时文件及无数据库引用的孤立文件 24 小时清理。作品、模板和已登记文件只由用户删除。删除仍被作品使用的素材返回 409；删除作品不删除消费历史。若要清理整个账户，先停止该账户任务再由受审计后台操作处理。

## 监控

`GET /api/health` 检查数据库连接；管理接口返回任务状态计数。监控 Celery generation/export 队列深度、任务 created/updated 时间差、failed/awaiting_confirmation 数量及错误原因。pipiapi 的 AppCall 与消费日志按 request_id 对账，消费日志迟到保持“结算中”，不要将缺失日志计为零。

`GET /internal/metrics` 提供按类型/状态划分的任务数、模型步骤状态、最旧任务排队秒数及最近 500 个已完成任务的平均耗时。它只供 Compose 内网采集，Next.js 不代理这个路径，API 服务也不映射宿主机端口。`ops/prometheus.yml.example` 和 `ops/pipi-ppt-alerts.yml` 可接入现有监控系统；通知渠道由部署平台配置。以上配置尚未在目标环境启用。Redis 本身的消息积压、磁盘空间和实际消费日志核对仍使用相应基础设施监控。

建议告警：最旧排队时间超过 5 分钟；运行任务超过 8 分钟；模型失败率/导出失败率超过基线；结算中超过 15 分钟；PostgreSQL、Redis 或素材卷剩余空间不足 20%。错误日志不得包含授权码、Cookie、Authorization、凭据密文或用户文件正文。

## 每日备份

仓库提供 `ops/backup.sh` 和配套 systemd service/timer，安装到部署主机后每日运行。配置 `PIPI_BACKUP_DIR` 与 `PIPI_BACKUP_RECIPIENT`（age 公钥），将私钥单独放在备份恢复系统；脚本把数据库和素材直接流式加密，不落地明文。脚本短暂停止原本运行的应用/Worker，等待请求收尾，再备份数据库和素材，结束时恢复这些服务。未完成的备份留在 `.incomplete` 目录，不作为成功备份。脚本和定时器尚未在目标主机执行。

使用平台现有备份调度，每日执行 `pg_dump -Fc` 到加密备份存储，并对 assets 卷进行一致性备份。备份加密密钥由现有机密管理保管；网站凭据加密密钥需单独备份，否则恢复后需要用户重新授权。保留至少七份每日备份和四份周备份。Redis 可由数据库 queued 状态重建，但应保留其 AOF 卷以降低恢复延迟。

如采用仓库脚本，配置现有备份存储的生命周期保留策略；脚本不会自动删除旧备份。启用 timer 前校验一次加密备份并在独立环境恢复。恢复时先验证 SHA256SUMS，使用 age 私钥解密，将 dump 用 pg_restore 写入空的专用数据库，并恢复素材卷及独立保管的 Fernet 密钥。禁止向已有生产数据库直接覆盖恢复。

恢复演练：先关闭新任务，恢复数据库与素材，确认归属/存储计数，再启动调度器。running 步骤中 calling/uncertain 不能按失败未消费处理。恢复后检查两名用户的下载隔离和历史消费关联。

## 回滚

先关闭本站 policy.enabled 和必要时 pipiapi `PIPI_PPT_ENABLED`，等待运行请求完成或进入待确认。保留所有持久卷，部署前一版本镜像并检查健康与只读作品。不要通过回滚删除消费记录，不要再次运行未知消费状态的模型步骤。问题解决后再开放新任务。
